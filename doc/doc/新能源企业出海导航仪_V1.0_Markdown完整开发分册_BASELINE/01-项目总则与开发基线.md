# 第一篇 项目总则与开发基线

> 版本状态：V1.0-BASELINE（已确认并冻结）。

## 第1章 文档说明与版本控制

### 1.1 文档编制目的

本开发文档用于把《新能源企业出海导航仪》的产品构想、业务规则、数据体系、AI能力、系统架构和项目实施要求，转化为可以被产品经理、设计人员、数据人员、开发人员、测试人员、运营人员及Codex共同执行的统一工程基线。

文档解决四个核心问题：第一，明确V1.0“建设什么”和“不建设什么”；第二，把国家、政策、风险、项目、伙伴、用户、会员、线索等对象统一成可实现的数据与功能边界；第三，为AI顾问建立有来源、有时效、有权限、有复核的输出规则；第四，为需求评审、开发排期、测试验收和版本变更提供唯一依据。

本文件不是市场宣传材料，也不替代法律、税务、投资或工程尽调意见。平台中涉及监管许可、投资决策、税务处理和项目真实性的高风险结论，必须显示信息来源、更新时间和专业复核提示。

### 1.3 文档使用方式

方案C采用“三层一致”的文档组织方式：Word总文档是正式评审载体；Markdown分册是开发仓库中的可维护基线；Excel技术附件保存字段级、接口级、用例级和权限级清单。三类文件的章节、编号和版本必须相互关联。

开发启动前，应完成“需求基线确认—用户故事拆分—原型确认—数据字典冻结—接口契约确认—测试用例前置”的准备。开发人员不得仅依据界面截图实现业务规则；存在歧义时，以经批准的需求编号、规则编号和验收标准为准。

### 1.4 编制依据

本版依据此前确认的项目定位、初步实施方案、开发方案、国家统一数据结构、印尼样板国家要求、全球分层数据覆盖策略、AI出海顾问路线及企业服务闭环进行编制。外部法律法规、国家政策、项目与招投标信息属于动态数据，不在本章固化具体结论，后续应通过数据来源目录及更新SLA管理。

### 1.5 术语与缩略语

| 术语 | 定义 |
|---|---|
| MVP | V1.0最小可行产品，以验证核心用户价值与商业闭环为目标 |
| Basic Coverage | 国家基础覆盖，提供关键概览、基础指标、来源和更新时间 |
| Standard Coverage | 标准覆盖，在基础信息上增加较完整政策、风险、市场与机会信息 |
| Complete Coverage | 完整覆盖，具备可用于深度决策的系统化国家数据、证据链和人工复核 |
| RAG | 检索增强生成，即先检索结构化数据与知识资料，再由模型生成有引用的回答 |
| 数据证据链 | 从展示结论追溯到字段、来源文档、原始页面、采集时间和审核记录的关系 |
| 机会 | 可供企业判断和跟进的市场、项目、招标或合作信号，不等同于已核实商机 |
| 商机 | 经平台或商务人员验证，具备明确主体、需求、阶段与下一步动作的销售机会 |
| 高风险结论 | 可能显著影响法律合规、税务、投资、安全或重大商业决策的内容 |

### 1.6 文档分册关系

完整文档分为七篇四十三章。正文用于解释目标、规则和设计；Excel附件保存可执行清单；原型、架构图、流程图和ER图作为图形附件。每个功能需求应具有`FR-模块-序号`编号，每个非功能需求使用`NFR-类别-序号`，每个数据字段使用`实体.字段`，每个接口使用`API-模块-序号`，每个测试用例使用`TC-模块-序号`。

### 1.8 编制、审核与批准机制

文档采用“编制人—专业审核人—项目负责人—业务负责人”四级确认。产品需求由产品负责人编制，数据章节由数据负责人审核，AI章节由AI负责人审核，安全与架构章节由技术负责人审核，最终范围由项目负责人和业务负责人批准。

达到开发冻结条件时，必须满足：P0需求全部具备验收标准；关键页面流程无阻断；核心实体、字段、状态和枚举已定义；接口输入输出和错误处理明确；数据来源、更新时间与审核机制明确；AI高风险输出规则已确定；测试团队能够据此独立编写或执行用例。

### 1.9 需求变更与文档更新机制

需求变更按“提出—影响分析—评审—批准—更新—通知—验证”执行。影响分析至少包含业务价值、用户影响、数据影响、接口影响、AI影响、安全影响、开发测试工作量、上线风险和排期影响。

下列变更必须进入正式评审：P0功能新增或删除；角色权限扩大；会员权益改变；核心评分规则改变；数据来源或合法使用边界改变；AI回答边界改变；核心技术栈或部署方式改变。纯文案、无业务影响的样式修正可走简化流程，但仍应记录版本。

## 第2章 项目概述

### 2.1 项目背景

中国新能源企业在海外拓展过程中，通常需要跨国家、跨技术方向、跨语言收集政策、市场、项目、伙伴与风险信息。现有信息分散在政府网站、监管机构、多边开发银行、采购平台、行业机构、企业公告和当地媒体中，更新周期、口径、可信度和可访问性差异明显。

多数企业目前依赖人工搜索、零散报告、人脉询问和临时咨询完成前期决策，容易出现信息过期、来源不可追溯、国家之间不可比较、项目线索与企业能力不匹配、研究成果无法沉淀等问题。因此，本项目拟建设一个以统一国家数据库为底座、以AI出海顾问为交互入口、以项目和伙伴服务为转化路径的企业级出海决策平台。

### 2.2 行业核心痛点

| 痛点 | 典型表现 | 平台应对 |
|---|---|---|
| 信息分散 | 数据散落于不同语言和格式的网页、PDF、公告 | 统一采集、结构化和来源管理 |
| 口径不一 | 国家报告结构不同，难以横向比较 | 统一国家字段、指标与评分框架 |
| 时效不足 | 政策、项目状态变化后旧内容仍被使用 | 更新时间、有效状态、变更监控与失效机制 |
| 可信度不足 | 二手转载、项目真实性难判断 | 来源评级、交叉验证、审核与证据链 |
| 决策效率低 | 企业重复进行初步国家研究 | 国家筛选、对比、AI问答和报告生成 |
| 线索难转化 | 阅读内容后无法形成持续跟进 | 收藏、申请、CRM、咨询与撮合闭环 |
| AI幻觉风险 | 模型给出无来源或过度确定的结论 | RAG、结构化查询、引用、拒答和复核提示 |

### 2.3 项目总体定位

《新能源企业出海导航仪》定位为“面向中国新能源企业的全球国家数据库与AI决策服务平台”。它不是简单的新闻资讯站，也不是仅供下载报告的内容库，而是把国家选择、政策理解、风险识别、项目发现、伙伴匹配、报告产出和商务跟进连接起来的企业工作台。

平台首期主要服务光伏、储能、新能源装备、EPC、投资开发和综合能源服务等企业。行业模型应保留扩展能力，但V1.0优先聚焦新能源出海的共性决策问题，不在首期覆盖所有工业品类。

### 2.4 产品核心价值

对企业用户，平台提供更快的国家初筛、更一致的对比口径、更可追溯的政策和风险信息、更贴近企业画像的机会推荐，以及可复用的AI研究与报告能力。对平台运营方，项目形成可持续积累的数据资产、用户需求画像、商业线索和服务交易入口。

核心价值可概括为“五个统一”：统一国家结构、统一数据口径、统一证据链、统一AI入口、统一商业跟进。平台最终目标不是给出绝对决策，而是显著降低信息搜集成本、缩短初步判断周期，并让专业人员把时间投入到验证和落地。

### 2.5 建设目标

V1.0建设目标分为产品、数据、AI、业务和工程五类：

1. 建成可用的PC Web企业工作台及统一运营后台，H5承担内容传播和线索收集。
2. 建立所有国家可复用的数据标准，完成30—50个国家Basic覆盖、3—5个重点国家Standard覆盖，印尼达到Complete覆盖验收条件。
3. 建立国家筛选、国家详情、国家对比、政策风险、项目机会、伙伴资源、AI顾问和报告中心等核心模块。
4. AI回答能够调用结构化数据和RAG知识库，显示主要来源与更新时间，对证据不足或高风险问题执行提示、降级或拒答。
5. 实现注册、企业画像、收藏、详情申请、咨询申请、线索入库和CRM跟进的最小商业闭环。
6. 建立可持续的数据采集、审核、发布、纠错、失效和质量度量机制。
7. 建立可维护、可测试、可监控、可扩展的工程架构，为后续国家扩展和商业化迭代预留能力。

### 2.6 建设原则

| 原则 | 工程含义 |
|---|---|
| 统一优先 | 先统一国家结构、字段和流程，再增加国家与内容 |
| 证据优先 | 重要结论必须能够追溯来源和更新时间 |
| 人机协同 | 自动采集和AI提升效率，关键数据由人工审核 |
| MVP聚焦 | 首期优先完成可验证的核心闭环，控制复杂度 |
| 数据与权限前置 | 页面开发前明确字段、状态、可见范围和脱敏规则 |
| AI可控 | 模型输出受数据、权限、时效、引用和风险规则约束 |
| 可运营 | 每个模块必须考虑后台维护、质量监控和异常处理 |
| 可扩展 | 国家、语言、模型、数据源和商业产品均采用可配置设计 |

### 2.7 产品发展路径

第一阶段为V1.0 MVP，验证国家数据库、AI顾问和线索转化；第二阶段为V1.5商业化试点，完善会员产品、报告商品、咨询服务和重点国家深度数据；第三阶段为V2.0平台增强，扩展小程序、多语言、企业协作、项目撮合和更多外部数据连接；私有化部署、本地模型微调和海外多语言站点在具备明确客户与投入条件后单独立项。

### 2.8 与传统资讯网站的区别

传统资讯网站以文章和流量为中心，本平台以国家、政策、风险、项目、企业等结构化实体为中心。文章可以作为获客和解释材料，但不是数据资产的唯一载体。相同政策应进入统一政策实体，并关联国家、技术方向、有效期、影响对象和来源，而不是只存在于一篇文章中。

### 2.9 与咨询和项目撮合业务的关系

平台负责标准化初步研究、需求识别和线索沉淀；咨询团队负责深度定制、专业判断和交付；商务团队负责主体核实、合作沟通和项目推进。平台不应把未验证的机会包装为确定项目，也不应在缺乏授权时公开敏感联系人。所有对接申请进入CRM，由人工确认资格、范围和披露权限。

## 第3章 建设范围与MVP边界

### 3.1 总体建设范围

总体范围包括六个组成部分：用户侧PC Web工作台、H5传播入口、统一运营后台、结构化全球国家数据库、AI与RAG知识库、CRM及商业服务闭环。微信小程序保留接口和设计兼容，但作为P1能力，不作为V1.0上线硬条件。

### 3.2 V1.0 MVP建设范围

| 领域 | V1.0必须交付 | V1.0控制范围 |
|---|---|---|
| 用户端 | 注册登录、企业画像、国家导航、详情、对比、政策风险、项目伙伴、AI顾问、报告、收藏与申请 | 以PC Web为主，H5提供轻量页面 |
| 后台 | 数据、内容、来源、用户、会员、CRM、知识库、Prompt、审核、日志 | 不建设超复杂低代码平台 |
| 数据 | 全球统一结构、分层覆盖、印尼完整样板、来源和更新时间 | 不承诺一次性覆盖全球全部深度数据 |
| AI | 结构化查询、RAG问答、引用、报告生成、反馈与评测 | 不以模型微调作为首期前提 |
| 商业化 | 权益控制、人工开通、详情/咨询/对接申请、CRM跟进 | 暂不建设复杂在线交易结算 |
| 工程 | 多环境、权限、日志、监控、备份、CI/CD基础能力 | 不建设超出实际规模的微服务集群 |

### 3.3 P0、P1、P2、P3功能分级

- P0：没有该能力就无法验证核心价值或无法安全上线，必须进入V1.0。
- P1：明显提升体验或商业转化，优先在V1.0后半程或V1.5完成。
- P2：增强效率和规模化能力，根据真实用户反馈迭代。
- P3：远期探索，需要独立商业或技术验证。

任何P0需求必须同时具备负责人、需求编号、页面或接口归属、数据依赖、验收标准和测试用例。P1以下需求不得以隐性方式进入P0排期。

### 3.4 首期纳入范围

首期纳入：全球地图和国家列表；统一国家详情页；国家对比；政策和国家风险；项目、招标与市场机会；本地伙伴、中资企业和服务资源；AI问答和报告生成；注册、企业画像、会员权限；收藏、申请和CRM线索；数据采集、审核和质量后台；基本的系统安全、审计和运维能力。

### 3.5 首期暂不建设范围

V1.0暂不建设独立原生App、面向海外用户的完整多语言站、复杂在线支付与结算、全功能私域社群、完整企业内部协同套件、对全部国家的Complete覆盖、自动替代专家的法律税务结论、无人工校验的全自动项目撮合、为单一客户定制的私有化部署，以及以大量标注数据为前提的本地模型微调。

### 3.6 外部系统边界

V1.0可能集成短信或邮件、对象存储、地图、模型服务、搜索或向量存储、网页采集、企业认证及内容渠道。任何外部服务必须经过接口封装，不得把供应商特定逻辑散落在业务代码中；必须记录调用状态、费用、失败原因和重试结果，并提供可替换或降级方案。

### 3.7 数据建设边界

所有国家采用统一核心字段，但允许不同覆盖等级显示不同完整度。缺失值必须明确标识为“待采集”“不适用”“未核实”或“暂未公开”，不得用空字符串混淆状态。平台展示内容必须保存来源、采集时间、发布时间（如有）、适用期、审核状态和最后复核时间。

首期数据量验收以“覆盖国家数＋必填字段完成率＋来源合格率＋更新及时率＋抽检准确率”共同判断，不以单纯记录数量作为上线标准。

### 3.8 AI能力边界

AI可以进行信息检索、摘要、对比、解释、初步推荐和报告草拟，但不得在证据不足时生成确定性事实，不得绕过用户权限获取内容，不得把过期政策当作现行政策，不得替代专业人员出具法律、税务、投资或工程签署意见。

对于高风险问题，系统应优先返回可核实事实、来源和待确认项；当来源冲突、材料过期或无法验证时，应明确说明限制并建议人工复核。所有AI输出均需记录模型、Prompt版本、检索范围、引用来源、生成时间和用户反馈。

### 3.9 商业化功能边界

V1.0采用“权益配置＋后台人工开通＋申请线索＋人工跟进”的轻量商业模式。会员可控制数据深度、下载次数、AI额度、项目详情和伙伴对接资格。价格、合同、发票和复杂结算暂由线下流程承接，但平台应保存产品、权益、到期时间和服务记录。

### 3.10 MVP成功标准

MVP成功需要同时满足：核心P0功能通过验收；印尼完整国家样板通过覆盖验收；30—50个国家达到Basic标准；AI标准问题集达到约定的事实正确性、引用展示率和拒答合格率；种子用户可以独立完成“选国家—看政策风险—看机会—AI分析—生成或申请报告—提交咨询/对接”的闭环；平台能够将关键行为形成CRM线索并供商务跟进；连续试运行期间无阻断性安全或稳定性问题。

## 第4章 目标用户与核心场景

### 4.1 用户分类

| 用户类型 | 核心目标 | 关键权限/功能 |
|---|---|---|
| 游客 | 了解平台价值和部分国家内容 | 查看公开摘要、注册、提交基础表单 |
| 注册用户 | 进行基础国家研究 | 收藏、基础对比、有限AI问答 |
| 企业成员 | 基于企业画像获取推荐 | 深度数据、报告、申请和历史记录 |
| 企业管理员 | 管理本企业成员与资料 | 企业认证、成员和权限管理 |
| 企业会员 | 使用付费权益 | 会员数据、额度、下载和优先服务 |
| 数据编辑 | 采集和维护数据 | 草稿、导入、提交审核 |
| 数据审核 | 审核、退回和发布 | 审核、质量标记、发布/下架 |
| 运营人员 | 内容、活动、会员与用户运营 | 内容管理、配置、用户服务 |
| 商务人员 | 跟进线索和商机 | CRM、对接记录、阶段推进 |
| 系统管理员 | 系统配置与审计 | 角色、权限、字典、日志和系统配置 |

### 4.2 企业高层使用场景

企业高层关注“哪些国家值得优先投入、主要风险是什么、进入方式如何、下一步需要做什么”。系统应提供精炼的国家排序、关键指标、风险摘要、证据来源和可导出的管理层报告。高层视图不得堆砌原始资料，应突出结论依据、置信边界和关键待决策项。

### 4.3 海外市场人员使用场景

市场人员需要持续追踪国家政策、市场规模、竞争格局和进入条件。典型流程是设置关注国家和技术方向，查看更新提示，筛选政策与机会，收藏资料，调用AI形成市场摘要，并将重要内容输出为内部简报。

### 4.4 销售与商务人员使用场景

销售人员以发现可跟进机会、识别参与方和记录行动为主。系统应把项目收藏、详情申请、报告领取、AI高意向问题和伙伴对接申请转化为线索，并结合企业画像与行为形成可解释的线索评分。评分只用于排序，不自动替代商务判断。

### 4.5 EPC及项目人员使用场景

EPC与项目人员关注项目地点、规模、阶段、业主、资金来源、采购方式、时间节点、技术要求和参与门槛。项目详情必须区分已核实事实、来源推断和平台判断，并显示最近核实时间。招标文件解析需保留原文定位和提取结果，关键条款应允许人工修改。

### 4.6 投资开发人员使用场景

投资开发人员需要综合政策稳定性、市场需求、电力机制、准入限制、汇率与政治风险、项目质量和退出条件。AI可以生成初步筛查意见，但页面必须明确：平台信息仅用于前期筛选，正式投资决策应开展法律、税务、财务、技术和环境社会尽调。

### 4.7 法务合规人员使用场景

法务合规人员需要查询政策原文、主管机构、适用对象、生效日期、废止状态和核心义务。政策解读必须关联原始来源并显示是否经过人工复核；对翻译内容应保留原文和译文关系。系统不得把行业文章的观点标记为官方规则。

### 4.8 平台运营人员使用场景

运营人员负责国家专题、报告、活动页、会员权益和用户触达。后台应提供发布状态、定时发布、渠道参数、表单配置、转化数据和内容下架能力。所有影响会员权益或敏感数据展示的配置应进入审计日志。

### 4.9 数据审核人员使用场景

数据审核人员对来源权威性、字段映射、翻译、重复、有效期、实体关联和敏感信息进行检查。审核动作应支持通过、退回、要求补充、下架和标记争议；发布后的关键字段变更要保存旧值、新值、修改人、审核人和原因。

### 4.10 八类核心业务场景

| 场景 | 用户输入 | 平台处理 | 主要输出 | 闭环动作 |
|---|---|---|---|---|
| 选国家 | 企业能力、目标、技术方向 | 规则筛选＋评分＋AI解释 | 优先国家清单 | 收藏、对比、生成报告 |
| 看政策 | 国家、主题、时间 | 结构化过滤＋RAG解释 | 条款、影响、来源 | 关注更新、申请咨询 |
| 找项目 | 区域、技术、阶段、规模 | 项目筛选＋真实性与机会评分 | 项目/招标列表 | 收藏、详情申请、进入CRM |
| 找伙伴 | 国家、服务类型、能力 | 伙伴筛选＋审核等级 | 伙伴候选 | 对接申请、商务审核 |
| 控风险 | 国家、项目、风险类别 | 风险库＋证据检索＋提示规则 | 风险清单和缓释建议 | 专业复核、跟踪更新 |
| 做报告 | 模板、国家、企业画像 | 数据查询＋RAG＋模板生成 | 可编辑报告 | 下载、分享、咨询升级 |
| 跟线索 | 用户行为、申请、表单 | 线索创建、评分、分配 | 待办和商机阶段 | 商务跟进、结果记录 |
| 做撮合 | 已验证需求和供给 | 人工核验＋权限披露 | 对接方案 | 会议、纪要、后续服务 |

八类场景构成V1.0的业务主线。其中“选国家—看政策/风险—找项目/伙伴—做报告”验证产品价值，“申请—线索—跟进—咨询/撮合”验证商业闭环。任何新增功能都应说明其服务的核心场景、用户价值和衡量指标。

## 第一篇审核要点

1. 是否同意V1.0以PC Web为主、H5为辅、小程序为P1。
2. 是否同意全球30—50国Basic、3—5国Standard、印尼Complete的首期数据目标。
3. 是否同意复杂支付、独立App、完整多语言站、私有化和本地模型微调不进入V1.0硬范围。
4. 是否同意AI仅提供有来源的辅助研究，高风险结论必须提示复核。
5. 是否同意V1.0先以后台人工开通和线下成交承接商业化。
6. 是否同意以P0通过、数据覆盖、AI评测、用户闭环和试运行稳定性共同作为MVP成功标准。
